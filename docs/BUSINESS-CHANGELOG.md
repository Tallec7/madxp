## Semaine 18 — 28 Avril-4 Mai 2026

### 🎯 Pour le club (NLF, prospects)

- **Télécommande V2 : préférences sauvegardées en cloud par site/profil** (cette PR, ADR-102) — depuis le scoping localStorage de PR #688, les prefs (haptics, contraste, layout mobile/PC, taille de texte, widgets actifs score/chrono/breaking) étaient bien isolées entre clubs mais perdues à chaque changement de device. Un opérateur qui passait du PC tribune au PC régie retombait sur les defaults. Désormais, les prefs sont persistées en DB cloud par paire `(site, profil)` via une nouvelle table `remote_preferences` : un staff retrouve son layout "Régie pro sombre" et ses widgets sur n'importe quelle TV / PC / tablette du club. Backfill automatique : la première connexion DB pousse le cache localStorage si la DB est vide → aucun reset visible côté utilisateur. Endpoints protégés par PIN profil quand défini (cohérent ADR-058). Recents (vidéos récentes) restent en localStorage device-local (volume + privacy).
- **Télécommande V2 : icônes harmonisées cross-OS** ([cette PR](https://github.com/Tallec7/neopro)) — les 11 emojis Unicode de la Remote V2 (📷 modifier logo, 🔁 nouveau match, ⏸/▶ chrono, 💡 astuce breaking news, → période suivante, › chevrons prefs, ⚠/✓ statut erreurs vidéo) rendaient différemment selon iPad opérateur, tablette Android régie, PC Windows tribune ou PC Linux centre médias — parfois en tofu illisible. Migration vers une bibliothèque SVG inline contrôlée (`<app-r2-icon>` + registre Lucide MIT, 0 dépendance npm). Affichage pixel-identique partout, icônes teintables (rouge danger / blanc dark mode), accessibilité RGAA correcte (le lecteur d'écran lit "Modifier le logo" au lieu de "appareil photo emoji"). SPEC-V2-ICONS-01.
- **Télécommande V2 : 6 layouts au choix (3 mobile + 3 PC)** — l'opérateur régie pro qui pilote 30+ vidéos par match passait son temps à scroller : seules 3,5 vidéos étaient visibles sur mobile, et 3 sur PC 27 pouces. Nouveau système de préférence "Affichage" dans les prefs : Mobile {Liste dense recommandée régie / Cartes visuelles / Tableur compact} × PC {Centré confort / Sidebar+browse recommandée / Régie pro sombre [bêta]}. Mobile dense passe à ~9 vidéos visibles (+157 %), PC sidebar à ~18 (+500 %). Choix mémorisé par utilisateur, bascule instantanée sans reload. SPEC-V2-LAYOUT-01.
- Bibliothèque vidéo : badge `×N` sur les miniatures quand plusieurs entrées DB pointent sur le même fichier physique FTP. Évite la confusion "pourquoi je vois `2_MIN.mp4` deux fois ?" — au survol, une infobulle explique que le contenu est identique (détecté par checksum) et qu'un seul fichier est stocké côté serveur ([#673](https://github.com/Tallec7/neopro/pull/673)).
- **Multi-TV par hotspot Pi : un club peut désormais ajouter une 2ᵉ/3ᵉ TV en 5 min, sans tirer de câble** — un besoin client court terme (diffuser le même contenu sur 2 écrans à 10m d'écart) était déjà couvert par l'archi existante mais non documenté côté ops. Nouveau guide [`docs/guides/MULTI_TV_HOTSPOT_PI.md`](guides/MULTI_TV_HOTSPOT_PI.md) : BoM (Fire TV Stick 4K ~40€), procédure d'install pas-à-pas, checklist de validation (sync Stramatel, drift < 2s, Remote contrôle les 2 TV simultanément), troubleshooting (mDNS, drift, déconnexions). Aucun dev nécessaire — le Pi sert déjà nginx + Socket.IO + vidéos sur son hotspot, n'importe quel device en `http://neopro.local/tv` devient un écran. Trace décisionnelle dans [PROP-001 scénario E1](proposals/PROP-001-multi-tv-single-pi.md#scénario-e--pi-comme-hub-saas-local-nouveau-).
- **Télécommande V2 : fix du bug "tous les sites SaaS forcent V2 + préférences partagées entre clubs"** (cette PR) — en mode SaaS, tous les sites partagent le même domaine donc le navigateur partage le `localStorage` entre tous les sites visités. Conséquence : (1) un test ponctuel avec `?v2=1` collait V2 à tous les sites suivants même quand l'override `remote_v2` n'était pas activé dans le dashboard, et (2) les préférences UX (haptics, contraste, layout, vidéos récentes, widgets actifs) étaient mutualisées entre clubs au lieu d'être par site/profil. Fix : (a) le query param `?v2=…` n'écrit plus dans le localStorage, le feature flag du dashboard redevient autoritaire, et le navigateur nettoie automatiquement la clé legacy au prochain reload pour les utilisateurs déjà contaminés ; (b) les clés de préférences sont scopées `<base>:<siteId>:<profileId>` en SaaS (Pi natif inchangé). Détection : remontée Daisy 28/04. Impact monitoring : 16 smoke tests verts, 3 nouveaux assertions qui bloqueraient toute régression future.
- **Le bouton 🚀 "Déployer" depuis la fiche site fonctionne à nouveau** — depuis la création de l'onglet contenu de la fiche site, le bouton de déploiement rapide depuis une carte vidéo lançait toujours une erreur "Échec du téléchargement vidéo: Invalid URL" côté Pi. Le dashboard envoyait un chemin Pi-relatif au lieu d'une URL FTP absolue. Le bouton passe maintenant par le même flux que la "Library" globale (création d'une row content_deployments serveur-side, URL construite à partir du `storage_path`). Bénéfice transverse : les déploiements depuis la fiche site sont désormais trackés (progress, retry auto, alerte stuck deployment, canary monitor) — avant ce fix, ces déploiements étaient invisibles côté monitoring.
- **Régie pro PC C : preview vidéo réel dans la télécommande** (cette PR) — le composant `<app-r2-tv-monitor>` du layout PC C "régie pro 3-col sombre" affichait jusqu'ici un placeholder visuel (gradient + nom de la vidéo). L'opérateur broadcaster pro qui pilote 30+ vidéos par match devait soit lever la tête vers la TV club, soit ouvrir une fenêtre Chromium séparée. Désormais, le Pi 5 capture sa propre sortie HDMI et la diffuse à la Remote en MJPEG (~500 ms de latence, 640×360 / 10 fps / ~3 Mbps en LAN). Comme dans un car régie TV pro : le mini-moniteur live est intégré à la cabine, plus besoin de lever la tête. Single-subscriber (1 régie = 1 stream pour ne pas saturer la bande passante du Pi). Throttle automatique CPU/temp pour ne **jamais** dégrader la TV club (priorité absolue à la diffusion publique : si le Pi chauffe, c'est le preview qui s'éteint, pas la TV). Pi 4 reste sur le placeholder en V1 (hardware insuffisant, ré-évalué post-mesures Pi 5 prod). SPEC-V2-TVMON-01 + ADR-102 (MJPEG V1, WebRTC V2 conditionnel sur déclencheur client Premium).

- **URL admin club-grants corrigée** ([#657](https://github.com/Tallec7/neopro/pull/657)) — la modal "Clubs autorisés" sur les vidéos admin globales remontait des 404 (mauvais préfixe `/content/videos/.../club-grants`). 4 endpoints corrigés (load, ajout, retrait, vue club). Plus d'erreur console quand un super_admin gère les accès clubs aux vidéos partagées.
- **Audit FTP : moins de faux positifs "Introuvable"** ([#660](https://github.com/Tallec7/neopro/pull/660)) — Hostinger refuse parfois les requêtes HEAD (timeout/5xx) alors que les fichiers existent. Le CRON marquait à tort des vidéos saines comme "introuvables" (~400 false positives observés en prod le 27/04). Nouvelle stratégie : HEAD timeout → retry GET Range minimal avant de persister le warning. Côté UI, deux badges distincts : 🔴 ❌ Introuvable FTP (404 confirmé, bloque) vs 🟠 ⚠️ Non vérifié (probe failed, info seulement). Dashboard plus fiable.
- **"Retirer du site" SaaS : plus de 404 utilisateur** ([cette PR](https://github.com/Tallec7/neopro)) — sur NLF Handball, cliquer "Retirer du site" sur certaines vidéos affichait une erreur rouge `404 Lien vidéo-site non trouvé`. Cause : le bouton est exposé pour toute vidéo cloud visible côté super_admin, mais le handler renvoyait 404 dès que la pivot `site_videos` n'avait pas la liaison — ce qui arrive normalement (vidéos cloud fleet-wide visibles sans liaison formelle). Fix d'idempotence : si la liaison n'existe pas, l'état désiré est déjà atteint → 200 + flag `alreadyUnlinked`, log `info` pour observabilité. Smoke test garde-fou ajouté pour empêcher la réintroduction du 404. Plus de faux échec côté admin.
- **Bouton "Remplacer le fichier" : fix critique** ([cette PR](https://github.com/Tallec7/neopro)) — depuis la livraison de #647, le bouton uploadait silencieusement TOUS les replaces sous le même nom `"undefined"` côté FTP, écrasant à chaque opération. La DB marquait la vidéo `ready` mais l'URL HTTP du fichier réel ne recevait jamais d'écriture → 404. 12 vidéos finissaient zombies (visibles en DB mais introuvables côté TV). Cause : 1 ligne lisait une colonne aliasée (`existing.storage_path` au lieu de `existing.url`). Fix + smoke test garde-fou inversé (verrouillait littéralement le bug) + ADR-100 documente le contrat de l'alias. Backfill manuel des 12 zombies à faire après deploy.
