- **Mini-écran régie pro stable côté SaaS** (ADR-104 + ADR-105, [#725](https://github.com/Tallec7/neopro/pull/725) → [#751](https://github.com/Tallec7/neopro/pull/751), ~15 PRs) — pivot de transport pour le mini-écran live de la Remote V2 PC C : (1) **côté SaaS** (ADR-104), abandon du flux MJPEG via Socket.IO (incident 429 — Cloudflare rate-limit en mode SaaS multi-tenant) au profit d'un HTTP pull périodique du dernier snapshot. Kill-switch déployé d'urgence ([#728](https://github.com/Tallec7/neopro/pull/728)) puis pivot ; (2) **côté Pi local** (ADR-105), remplacement du transport MJPEG par une iframe locale qui charge directement la TV Pi en mini-écran scaled (60×38 dans la card hero). Plus rapide, plus robuste, 0 dégradation de la TV publique. La régie distante (mobile hotspot derrière NAT) garde le flux HMAC + token TTL 5 min livré en sprint précédent.
- **Bascule progressive du dashboard et du SaaS sur Cloudflare Pages** (ADR-071 phases 2-3, [#729](https://github.com/Tallec7/neopro/pull/729) → [#751](https://github.com/Tallec7/neopro/pull/751), ~20 PRs) — migration de l'hébergement front depuis Hostinger (FTP) vers Cloudflare Pages. Le dashboard `app.neopro.tv` et le SaaS `play.neopro.tv` sortent désormais du même projet Pages unique (`neopro-frontend-prod`, Option A) avec routing `/saas/*` traité par une Pages Function. Bascule sans casser : flag `vars.HOSTING == 'cloudflare'` côté GitHub Environment, jobs Hostinger skip auto, retour arrière par simple flip. **Bénéfice club** : edge global (latence -200 à -400 ms hors Europe), HTTPS automatique, déploiements 5× plus rapides (1m53 vs 11min). Trois incidents traités en flight et corrigés : (a) cache poisoning des chunks JS Angular (HTML 1 an servi pour des URLs `*.js` à cause d'un mismatch SPA fallback + Link auto-injection — Pages Function explicite avec content-type strict), (b) sub-routes SaaS qui retournaient 404 (workaround route stubs statiques `/saas/foo/index.html`), (c) verify CI cassé sur cold-start TLS (timeout 15s → 30s).
- **Télécommande V2 : sélection de profil + saisie de PIN restaurées** (cette PR, ADR-058 + ADR-092) — depuis le rollout V2, deux écrans présents en V1 manquaient au boot : (1) l'écran plein écran de **sélection de profil** quand un site SaaS a >1 profil (typiquement un club multi-équipes ou un complexe sportif multi-sports) — l'utilisateur arrivait directement sur un profil par défaut arbitraire ; (2) l'écran de **saisie de PIN** (ADR-058) quand un profil est protégé par code — un toast d'erreur générique remplaçait le pavé numérique, rendant le profil inutilisable depuis V2. Désormais, V2 reproduit exactement le contrat V1 : `bootView` gate l'UI tant qu'aucun profil n'est choisi, l'overlay PIN apparaît plein écran si requis, et le changement de profil depuis le menu engrenage déclenche aussi le PIN si nécessaire. Mode démo (sélection club avant présentation) également porté. Débloque le sunset V1 prévu **1ᵉʳ nov 2026**.
- **Télécommande V2 : préférences sauvegardées en cloud par site/profil** (cette PR, ADR-102) — depuis le scoping localStorage de PR #688, les prefs (haptics, contraste, layout mobile/PC, taille de texte, widgets actifs score/chrono/breaking) étaient bien isolées entre clubs mais perdues à chaque changement de device. Un opérateur qui passait du PC tribune au PC régie retombait sur les defaults. Désormais, les prefs sont persistées en DB cloud par paire `(site, profil)` via une nouvelle table `remote_preferences` : un staff retrouve son layout "Régie pro sombre" et ses widgets sur n'importe quelle TV / PC / tablette du club. Backfill automatique : la première connexion DB pousse le cache localStorage si la DB est vide → aucun reset visible côté utilisateur. Endpoints protégés par PIN profil quand défini (cohérent ADR-058). Recents (vidéos récentes) restent en localStorage device-local (volume + privacy).

(1) **Multi-écrans** : V2 envoyait `displayIndex: number` que la TV ignorait — toutes les commandes hit toutes les TVs, donc sélectionner un écran spécifique dans la Remote V2 était sans effet. Désormais chaque emit Remote V2 inclut un commandId, l'analytics retrouve la même précision qu'en V1. (3) **Diffusion locale** : V2 ne broadcastait plus via BroadcastChannel — les TV co-localisées (même origine, ex: TV+Remote ouvertes dans un même navigateur) recevaient les commandes uniquement via Socket.IO (passage forcé par le Pi). ### 🛡️ Pour la robustesse

- **Hotspot NLF : 5 bugs cumulés résolus — le réseau WiFi du club fonctionne à nouveau** (commits `9cee706d`, `70910ada`, `73efe1f2`) — lors d'un match NLF, les appareils des spectateurs ne pouvaient ni se connecter au hotspot NEOPRO-NLF ni accéder à internet. Diagnostic et fix en session : (1) le routage IP était désactivé (`ip_forward=0`) → aucun paquet ne transitait entre les appareils et internet ; (2) le pare-feu NAT était mal configuré (masquerade sur la mauvaise interface WiFi) ; (3) `www.apple.com` était redirigé vers le Pi → iOS marquait le réseau "captive bloqué" et coupait tout ; (4) même problème pour Android avec `play.googleapis.com` ; (5) la config hostapd datait de la première installation (sans PMF, sans HT capabilities, limité à 10 clients) → les iPad ne pouvaient pas s'associer. Corrections permanentes : `setup-captive-portal-iptables.sh` corrigé (ip_forward + NAT), template `dnsmasq.conf` nettoyé des redirects cassants, `install.sh` passe désormais la bonne interface uplink, `fix-hotspot.sh` ne redémarre plus hostapd s'il tourne déjà (évite d'éjecter les clients). Audit réseau complet documenté dans `docs/clients/NLF-NETWORK-AUDIT-2026-05-02.md` pour référence future.
- **Kiosk Pi : fix du watchdog qui se kamikazait au boot** (cette PR) — au démarrage du Pi, ~35 s après le lancement de Chromium, le watchdog tuait son propre kiosk et déclenchait un restart inutile (TV figée 30 s sur le boot splash). Cause : la heuristique anti-fenêtre-parasite (qui surveille qu'une autre app — VLC, xdg-desktop-portal — ne vienne pas voler le focus) acceptait uniquement les titres contenant `Chromium`/`Neopro`. Or au boot, avant que l'Angular fasse son `setTitle("Neopro TV")`, Chromium nomme sa fenêtre par l'URL : `localhost_/tv` — aucun match → kill auto. Désormais la whitelist inclut aussi `localhost`, `about:blank`, `/tv`, `/remote`. Détecté sur debug bundle Pi NLF du 2026-05-01 (2 restarts dont 1 faux positif).
- **Télécommande V2 : 4 trous d'orchestration colmatés (sélecteur d'écran, breaking news, options match, retour automatique sur cible orpheline)** (cette PR) — audit déclenché par retour terrain Daisy 2026-05-01. Quatre régressions silencieuses bloquaient l'usage réel V2 alors que le contrat backend était déjà en place : (1) **N display invisible** — la sheet "Cible vidéo" (Tous / #0 / #1) ne s'affichait pas en V2 même avec 2 écrans connectés, alors qu'elle marche en V1. Cause : V2 ne demandait pas le snapshot serveur au boot (`request-state`) → la liste restait vide jusqu'à une (dé)connexion TV. Désormais request-state émis comme V1.
