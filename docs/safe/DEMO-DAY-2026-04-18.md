## TL;DR — Ce que le client verra changer dès lundi

1. **La télécommande MADXP fonctionne désormais même sans internet dans le club** (hotspot local du Raspberry).

## 1. Ce qui a été livré — version métier

### 🎮 Télécommande cloud V2 (ADR-059 → ADR-062)

**Avant** : télécommande centralisée dans le cloud uniquement. Si le club perd internet, le staff perd le contrôle de la TV.

**Maintenant** :

- **3 couches de résilience** : cloud → hotspot Pi local → PWA installable sur mobile.
- **Menu Préférences** intégré (UX) pour personnaliser l'affichage.
- **Panneau admin** de gouvernance des options (qui voit quoi selon son rôle).
- **Runbook de tests T1 à T15** livré au support — on sait exactement quoi tester avant chaque déploiement.

**Ce qu'on peut dire au client** :

> « Votre télécommande fonctionne même si votre box tombe. Le Pi prend le relais via son hotspot local, et votre staff peut installer l'app sur son téléphone. »

### 💻 SaaS streaming sécurisé (ADR-068)

**Avant** : les clubs SaaS (mode navigateur, sans Raspberry) n'avaient pas de canal de diffusion vidéo industrialisé.

**Maintenant** :

- **URLs signées** via proxy Node.js → les vidéos ne sont pas exposées en clair.
- **Supervision Prometheus** active → on mesure la latence, le taux d'erreur, et on a une alerte automatique en cas de dégradation.
- **Garde-fou anti-régression** intégré aux tests smoke (le bug "routes dans le mauvais ordre" ne peut plus revenir).
- **Visibilité des vidéos admin-déployées** restaurée côté club SaaS.

**Impact commercial** : on peut désormais vendre du SaaS pur (sans hardware) avec la même qualité de service qu'un club équipé Pi. **C'est un nouveau segment de marché débloqué.**

### 🔐 Sécurité PIN par profil (ADR-058 Phases 1 → 2C)

**Avant** : un PIN unique par site pour la télécommande.

**Maintenant** :

- **PIN différencié par profil** (super_admin, admin, operator, club).
- **Migration automatique** des anciens PIN → zéro action client.
- **Self-service club** : le club gère le PIN de son site depuis son portail.
- **Alerte email en cas de burst** (plusieurs échecs rapides = tentative d'intrusion).

**Ce qu'on peut dire au client** :

> « Chaque profil a son code d'accès. Si quelqu'un essaie de forcer, vous êtes prévenu par email. »

### ⚙️ Socle technique renforcé (ADR-063 → ADR-069)

Pour le métier, c'est invisible. Pour le produit, c'est fondamental :

- **ADR-063** : les warnings socket transients ne polluent plus les alertes (→ moins de faux positifs au support).
- **ADR-064/065/066** : unification des types vidéo côté Pi (→ prévient les bugs de compatibilité lors des futures features).
- **ADR-067** : décision architecturale assumée de **refuser** une unification monolithique qui aurait alourdi le code.
- **ADR-069** : **Delivery Strategy pattern** — le mécanisme qui choisit entre livraison Pi vs. SaaS est maintenant extensible proprement, avec métriques.
