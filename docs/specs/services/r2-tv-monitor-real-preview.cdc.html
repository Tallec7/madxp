TL;DR métier

L'opérateur régie pro qui pilote le match passe son temps à lever la tête vers la TV pour vérifier ce qui passe à l'antenne. On ajoute un mini-écran intégré à sa télécommande qui montre la vidéo en direct, comme dans un car régie TV pro.

Premier livrable simple (MJPEG) en LAN, ~500ms de retard accepté, déployable en 4 jours sur Pi 5. Évolution WebRTC plus tard si la latence devient bloquante.

Risque principal : ne jamais dégrader la qualité de la diffusion publique sur la TV. Tout le design tourne autour de cette garantie.

1. Contexte & objectifs mesurables

🎯 Client Cible : opérateur régie broadcast pro qui pilote 30+ vidéos par match en mode régie statique (cf. SPEC-V2-LAYOUT-01 §5C, layout PC C "Régie pro 3-col sombre"). Ce profil :

  • Ne quitte pas son poste pendant 90 min de match.
  • Pilote depuis un PC fixe ou un MacBook posé en cabine.
  • Doit savoir en permanence ce qui passe à l'écran TV (boucle live, lecture ponctuelle, sponsor).
  • Aujourd'hui : lève la tête vers la TV club ou ouvre une fenêtre Chromium avec l'URL Pi en preview manuelle. UX dégradée.

Le composant <app-r2-tv-monitor> existe déjà dans le code (cf. raspberry/src/app/components/remote-v2/parts/r2-tv-monitor.component.ts) mais c'est un placeholder visuel — gradient orange + nom de la vidéo + status LIVE/MANUAL/IDLE — pas de vraie image. Cette spec ajoute le vrai stream.

La qualité de la TV club ne doit jamais être dégradée par l'activation du preview. Concrètement : 0 frame drop additionnel, pas d'audio glitch, pas de freeze. 2. 3 options techniques comparées

Option A — MJPEG over HTTP Recommandé V1

Le Pi expose un endpoint HTTP qui renvoie un flux multipart/x-mixed-replace (séquence d'images JPEG concaténées). La télécommande consomme via <img src="..."> nativement (le navigateur gère le streaming).

Avantages : zéro WebRTC à orchestrer, marche dans <img> sans JavaScript, pas de signaling, pas de NAT traversal LAN, instantané à brancher.

Inconvénients : pas d'audio (pas grave ici), latence ~300-700ms côté client (re-rendering frame-by-frame), bande passante non-négligeable (~2-5 Mbps à 10 fps en 640×360 JPEG q=70).

Option B — WebRTC peer-to-peer

Pi devient un peer WebRTC qui streame H.264 vers la télécommande. Signaling via Socket.IO existant. ICE candidates → connexion directe LAN (TURN serveur cloud uniquement en fallback NAT).

Avantages : latence sub-200ms, encodage H.264 hardware Pi 5 (V3D) → BW 5-10× plus efficace que MJPEG, audio possible.

Inconvénients : complexité orchestration énorme (signaling, ICE, codec negotiation, peer reconnect), TURN obligatoire pour les régies derrière CGNAT mobile, impact CPU si software fallback (Pi 4 sans HW H.264 efficient encode).

Option C — HLS / LL-HLS

Pi expose un manifeste HLS + segments MP4 (CMAF). Télécommande consomme via <video> HTML5 (Safari natif, hls.js ailleurs).

Avantages : standard cloud, scalable (CDN), tooling éprouvé, fallback navigateur natif sur Safari.

Inconvénients : latence 1-3 s même en LL-HLS (≥ 3× la cible V1), nécessite transcoding live H.264 sur Pi = coût CPU/GPU significatif, complexité orchestration manifest.

3. Recommandation & rationale

🎯 Recommandation : MJPEG en V1, WebRTC en V2 sur déclencheur

V1 (P0+P1) = MJPEG over HTTP sur LAN. V2 (P2, post-validation prod) = WebRTC ajouté en alternative côté Pi, négocié via Socket.IO selon capacité réseau.

Pourquoi pas WebRTC d'emblée

  • Coût ROI déséquilibré : 10 jours dev pour gagner 200ms vs 4 jours pour 500ms. La régie n'est pas un live broadcaster TV qui a besoin de sync sub-second — c'est un opérateur qui veut un confort de monitoring.
  • NAT/TURN : dès que la régie est sur 4G ou derrière un NAT symétrique, il faut un serveur TURN. C'est un nouveau composant infra à héberger, à monitorer, à payer.
  • Pi 4 fragile : la flotte historique Neopro a beaucoup de Pi 4. WebRTC software encode dépasse le seuil critique. Risque de dégradation TV.
  • Complexité de fallback : si WebRTC échoue (codec, ICE, peer state), on tombe sur quoi ? On revient au placeholder ? Pas une UX cohérente.

Pourquoi pas HLS

Latence inacceptable même en LL-HLS pour le use case "qu'est-ce que ma TV affiche maintenant". 1 seconde de retard → l'opérateur clique sur play et ne voit pas la vidéo réagir → il reclique → boucle de frustration. Disqualifié.

Pourquoi MJPEG en V1

  • Time-to-market : 4 j-h dev, déployable la semaine d'après.
  • Hardware-friendly Pi 5 : libjpeg-turbo + capture canvas Puppeteer = ~10 % CPU. Marge confortable sous le seuil critique 15 %.
  • Robustesse : si le flux tombe, le <img> arrête juste de bouger. Pas de crash. Le placeholder peut prendre le relais via un timeout sur onerror.
  • Migration future propre : si on ajoute WebRTC en V2, le contrat Socket.IO reste compatible (capability negotiation). Pas de retour arrière requis.

Déclencheurs de la migration V2 → WebRTC

  • Plainte client "preview lag" mesurée > 700ms en moyenne sur 7 jours en prod.
  • Client Premium qui demande sub-200ms contractuellement (broadcaster pro, fédé, chaîne TV).
  • Objection commerciale récurrente sur le démo PC C.

Sans ces signaux, on reste en MJPEG. C'est suffisant.

Côté Pi — nouveau service tv-preview.service.js

Nouveau module dans raspberry/server/services/ (le serveur Socket.IO local Pi déjà actif sur :3000, cf. .claude/rules/raspberry.md). Pattern orchestrateur + service.

Capture de la frame

Trois approches possibles, à benchmarker côté dev :

  1. Puppeteer screencast sur l'instance Chromium kiosk déjà ouverte (Chrome DevTools Protocol Page.startScreencast) — donne directement des frames JPEG. Reco
  2. X11 capture (xwd / ffmpeg -f x11grab) — plus lourd, mais pas de couplage à Chromium.
  3. DRM screencopy (Wayland) — futur-proof si on bascule sur Wayland un jour, ne pas implémenter en V1.
🛡️ Garde-fou Pi 5 GPU V3D (cf. .claude/rules/raspberry.md)

Le kiosk-watchdog Pi 5 utilise déjà le driver V3D natif sans flags GPU custom (ADR documenté). N'AJOUTE PAS de flag Chromium pour la capture. Reuse le mécanisme GPU_DECODE_FALLBACK_FILE existant : si le preview cause un crash hardware, on tombe automatiquement en software decode + on désactive le preview pour 30 min via le fallback file.

Encodage JPEG

// raspberry/server/services/tv-preview.service.js
const turbo = require('@julusian/jpeg-turbo');

function encodeFrame(rgbaBuffer, width, height) {
  return turbo.compressSync(rgbaBuffer, {
    width, height,
    format: turbo.FORMAT_RGBA,
    quality: 70,                  // sweet spot taille/qualité
    subsampling: turbo.SUBSAMPLING_420,
  });
}

Cible 640×360 / 10 fps / quality 70 = ~3 Mbps. Si stress détecté, throttle automatique :

  • CPU > 80 % continu pendant 5 s → 5 fps
  • CPU > 90 % continu pendant 5 s → coupure preview, retour placeholder côté Remote
  • Temp > 75 °C → coupure immédiate (priorité absolue à la TV)

Endpoint HTTP multipart

// Mount sur le serveur Express déjà actif côté Pi (socket-server (Express + Socket.IO))
app.get('/preview.mjpeg', requireSiteAuth, (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'multipart/x-mixed-replace; boundary=frame',
    'Cache-Control': 'no-cache, no-store',
    'Pragma': 'no-cache',
    'Connection': 'close',
  });

  const sub = previewBus.subscribe((jpegBuf) => {
    res.write(`--frame\r\nContent-Type: image/jpeg\r\nContent-Length: ${jpegBuf.length}\r\n\r\n`);
    res.write(jpegBuf);
    res.write('\r\n');
  });

  req.on('close', () => sub.unsubscribe());
});

🛡️ Infra Le port :3000 est déjà utilisé par socket-server. Pas de nouveau port à ouvrir : on monte la route dans le Express existant (socket-server), avec auth identique au reste du panel.

Côté Remote V2 — composant enrichi

Le composant R2TvMonitorComponent (cf. raspberry/src/app/components/remote-v2/parts/r2-tv-monitor.component.ts) gagne :

  • Un nouvel input previewUrl: string | null (résolu par le parent via Socket.IO event tv-preview:capability).
  • Un état interne streamHealthy: boolean (true = on affiche la balise <img>, false = placeholder visuel actuel).
  • Détection des erreurs : onerror sur l'<img> + watchdog 3 s sans frame (via Image load events) → bascule placeholder.
  • Reconnexion auto : retry 1 s, 2 s, 4 s, 8 s (backoff exponentiel cap 30 s).
// r2-tv-monitor.component.ts — additions

@Input() previewUrl: string | null = null;
@Input() previewEnabled = false;     // gated par feature flag + layout PC C

streamHealthy = signal(false);
private reconnectTimer?: number;
private backoffMs = 1000;

onImgError(): void {
  this.streamHealthy.set(false);
  this.scheduleReconnect();
}

onImgLoad(): void {
  this.streamHealthy.set(true);
  this.backoffMs = 1000;     // reset backoff sur succès
}

Template :

<!-- branche stream live -->
<img *ngIf="previewEnabled && previewUrl"
     [src]="previewUrl"
     class="r2-tv-monitor__stream"
     [class.is-healthy]="streamHealthy()"
     (load)="onImgLoad()"
     (error)="onImgError()"
     alt="" />

<!-- placeholder fallback (toujours rendu, masqué quand stream healthy) -->
<div class="r2-tv-monitor__placeholder"
     [class.is-hidden]="streamHealthy()">
  ...icône + nom + status (template actuel)
</div>

Discovery — comment Remote sait où chercher

Le composant ne hardcode pas l'URL. Le parent RemoteV2Component écoute un event Socket.IO tv-preview:capability émis par le Pi à la connexion :

// Pi → Remote (via socket-server local)
{
  "event": "tv-preview:capability",
  "data": {
    "available": true,
    "transport": "mjpeg",                              // futur : "webrtc" en V2
    "url": "http://pi.local:3000/preview.mjpeg",    // résolu côté Pi
    "resolution": { "w": 640, "h": 360 },
    "fps": 10,
    "version": "1.0"
  }
}

Si l'event n'arrive pas dans les 2 s suivant la connexion, le composant ne tente jamais le stream et reste en placeholder. Pas de retry sauvage qui casserait le LAN.

Événements Socket.IO ajoutés

Endpoint REST ajouté

GET /preview.mjpeg Multipart x-mixed-replace, JPEG frames. Auth via cookie session ou query token (cf. §6).

Versioning

Champ version: "1.0" dans tv-preview:capability. Si le Pi annonce une version > majeure connue par la Remote, la Remote ignore et reste en placeholder. Permet d'introduire WebRTC en version: "2.0" sans casser les Remote anciennes.

6. Sécurité

Modes Pi vs SaaS (cf. .claude/rules/context.md)

ModeRéseau Pi accessible depuisAuth requise
Mode Pi (matériel club) Hotspot du Pi (LAN privé) ou Wi-Fi club (LAN privé) Cookie session opérateur du socket-server (port 3001) — déjà en place
Mode SaaS (navigateur seul, ADR-037) Pas de Pi physique — preview désactivé N/A — composant retombe sur le placeholder
Mode demo Pas de Pi physique N/A — placeholder uniquement

L'event tv-preview:capability est émis uniquement en mode Pi avec hotspot ou LAN actif. En SaaS/demo, l'event n'arrive jamais → placeholder par défaut. Pas de tentative de stream.

Auth de l'endpoint MJPEG

L'opérateur connecté à la Remote a déjà un cookie session-pi issu du socket-server (auth basique partagée hotspot). Pour les <img> cross-origin, le cookie est envoyé automatiquement si SameSite=Lax et même origine LAN.

Si la Remote tourne en cloud distant (rare mais possible), on émet un token éphémère 5 min via Socket.IO et on l'inclut en query string :

"url": "http://pi.local:3000/preview.mjpeg?t=eyJhbGc..."

Le Pi valide la signature HMAC avec une clé partagée connue de tous les composants (déjà en place pour les commandes existantes — cf. command-dispatch.js).

CSP côté Remote

La Remote charge actuellement les ressources en 'self' (cf. .claude/rules/raspberry.md). Le stream MJPEG vient d'une URL http://pi.local:3000/... qui peut violer la CSP.

Options :

  • Reco : étendre img-src uniquement à http://*.local:3000 et http://192.168.4.1:3000 (IP hotspot Pi). Pas de changement de script-src.
  • Alternative : proxy via le Pi socket-server (le Pi proxifie son propre stream sur :3000 → :8080) — plus complexe, pas la peine si la CSP img-src peut être assouplie.

Risques

Sniffing LAN Le LAN club est privé. Le sniff potentiel du flux par un client tier WiFi → identique au sniff de la TV elle-même (qui est publique de toute façon). Risque accepté.
Replay du token Token TTL 5 min. Régénération auto.
DDoS du Pi Le Pi limite à 1 connexion concurrente sur /preview.mjpeg (single-subscriber). 2e connexion → 429 Too Many Requests.

Coexistence avec la diffusion principale

Test obligatoire avant merge : 90 min de match simulé (lecture vidéos en boucle + lecture ponctuelles) avec preview actif vs sans preview. Mesurer :

  • Frame drops sur la TV (via chrome://media-internals)
  • CPU moyen + pic + temp Pi 5 (via vcgencmd measure_temp et top)
  • Aucune dégradation visible audio (si applicable) ni vidéo

Si delta > seuils → on retravaille la capture (passer 5 fps, baisser quality JPEG, ou software fallback).

9. Tests & recette

Tests unitaires côté Remote

  • R2TvMonitorComponent : onImgError bascule sur placeholder, onImgLoad rétablit, backoff exponentiel respecté
  • Reconnect timer cleanup sur ngOnDestroy

Tests smoke côté Pi (cf. .claude/rules/testing.md)

  • Nouvelle suite smoke-tv-preview.test.js qui vérifie :
    • Le service exporte les fonctions attendues
    • L'endpoint /preview.mjpeg est monté dans socket-server
    • L'event tv-preview:capability est émis à handleAuthenticated
    • Le throttle s'active à CPU > 80 %
    • Le subscriber unique limit fonctionne
  • Métriques Prometheus déclarées dans raspberry/server/services/metrics.service.js

Tests de charge (manuel avant prod)

  1. Pi 5 + TV club + 1 Remote PC C : 90 min match. Mesurer CPU, temp, frames TV.
  2. Pi 5 + 4G partagé : valider 5 fps fallback fonctionne.
  3. Pi 4 : valider que le preview est désactivé (capability emit available: false).
  4. Remote sur Safari, Chrome, Firefox, Edge : <img> multipart compatible partout.

Critères d'acceptation

  1. Sur Pi 5 + Remote PC C, le preview affiche bien la vidéo TV avec ≤ 700 ms de latence visible (test au chronomètre, clic play → frame visible).
  2. Drop wifi 5 s → reconnect auto et stream reprend en ≤ 3 s.
  3. Pi 5 charge CPU additionnelle ≤ 12 % en moyenne.
  4. Aucune dégradation TV mesurable (frame drops 0 sur 90 min).
  5. Pi 4 → preview désactivé proprement (placeholder, pas d'erreur console).
  6. Mode SaaS / demo → preview désactivé proprement.
  7. Sur autre layout que PC C → composant masqué (cf. fix scope PR #686).
  8. Sortir du layout PC C → Remote émet tv-preview:stop, le Pi cesse l'encodage.
  9. 2e Remote qui tente le stream → 429, la 1re continue.
  10. Dashboard Grafana tv-preview alimenté (frames/min, throttle events, subscribers).

10. Hors scope

  • Multi-Pi / dual-display : si un site a 2 TV (ADR-022), preview de quelle TV ? V1 = preview unique de l'écran principal. Multi-display preview = nouvelle spec.
  • Recording du preview pour replay opérateur : pas en V1.
  • Multi-télécommande qui consomment le même flux : limite single-subscriber Pi en V1. Si besoin réel, P2 ajoute fan-out cloud.
  • Audio : MJPEG ne supporte pas. WebRTC en V2 si demandé.
  • Annotations / overlays opérateur sur le preview (clickable hot-spots) : V3 si demande PM.
  • Preview dans Mobile B/C ou PC A/B : exclu — c'est une feature régie pro PC C uniquement (cf. invariant SPEC-V2-LAYOUT-01).
